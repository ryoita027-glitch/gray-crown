## 6. GitHub Actions/アセット/古い試作のコスト管理

**確認済みの履歴**：Phase1統合SUCCESS 37967259690 約283秒、Phase3 acting SUCCESS 37970478373 約154秒、同Triton SUCCESS 37970484136 約323秒、Ryune art v2 SUCCESS 37969043360 約264秒。これらは**run開始〜最終更新の実経過**であり、GitHubの**課金minutesそのものではない**。直近Phase5は約5秒で0 job steps。**残りの課金分・請求/ブロックの原因は未確認**。

実行案：
1. **push時**：`node tests/check-syntax.js`、Node単体・source locks・Story/event/セーブ整合性など安価なテスト。変更パスで関係する検査を選ぶが、最終のすべてのゲートは省略しない。
2. **統合/採用候補時**：既存`npm run check`とChromiumを**一度だけインストール**した1本の統合ジョブで、段階E2E→main v23真の保存→新しいマップE2Eを順番に実施。ブラウザ成果物7日程度、失敗でも必要ログとPNGを保存。
3. **夜間/手動の包括試験**：再現性のある長時間/3画面幅/多数の戦闘シード/実機検証。現時点で勝手に有料CIを作動させない。
4. 失敗したrunの`steps=null`ならすぐpush再試行ではなく**Actions画面の利用上限/請求/規約・check-run annotations・runner availability**を先に確認。
5. **アセット**：Git blob容量とブラウザ転送量を分けて測定。重複PNGは必ず使用経路/ハッシュ参照から整理し、fallback・比較実験を闇雲に削除しない。manifest上に`active/fallback/experiment/superseded`を付け、production bundleで参照されないものだけ候補削除。
6. **バージョン固定**：依存/Canvas/描画切替/アニメーションfps/セーブ状態/CIランナーの変更を独立PRに分け、前後の起動・メモリ・FPSを数値と画像で比較する。
